# 构建与打包

## 0. 前置

| 依赖 | 版本 | 说明 |
|---|---|---|
| Xcode Command Line Tools | Swift 5.9+ | `swift-tools-version: 5.9` |
| Dart SDK | 3.10.x 或更高 | 只用于编译 `MyNASCore`，运行时不需要；本轮验证使用 **3.13.5**（stable，macos_arm64） |
| macOS | 13.0+ | 部署目标，且**仅 arm64** |

> Dart SDK 不常驻仓库。`tools/install-mynas-core.sh` 按
> `DART_SDK` 环境变量 → PATH 里的 `dart` → 常见安装位 依次找，
> 找不到才需要显式设 `DART_SDK=<SDK 根目录>`（含 `bin/dart` 与 `bin/snapshots`）。
> 注意是 `DART_SDK`，没有 `_HOME` 后缀。

## 1. Swift 侧

```bash
bash scripts/build.sh app          # swift build --product FlashFind2App
bash scripts/build.sh test         # 基线：1824 项（7 项自动跳过），0 失败
```

依赖是**钉死的**：`Package.resolved` 入库，`Package.swift` 里 MCP SDK 用 `exact`
而不是 `from`（0.x 的 minor 是破坏性变更）。跑测试与打包都带
`--only-use-versions-from-resolved-file`；跑完 `git status Package.resolved`
应当是空的，不是空的就说明有人动了依赖而没说明原因。

## 2. Dart 搜索核心

```bash
bash scripts/build.sh core         # 底层：tools/install-mynas-core.sh
```

产物落在 `Resources/MyNAS/bin/mynas-core`（Dart AOT 可执行）。
**注意**：AOT 产物不可复现，同源码两次编译的二进制也不同。
如果要复用既有产物，务必先与已发布包里的那份逐字节比对。

核心与客户端之间有**协议版本闸门**：

```
MyNASCore/lib/protocol.dart            const int coreRevision
Sources/FlashFindCore/MyNASProcessBridge.swift   static let expectedCoreRevision
```

两边必须一致，否则启动即报错退出，不会带着版本错位跑下去。

## 3. 打包

```bash
bash scripts/build.sh package --release \
    --icon Resources/Brand/ShanXun.icns \
    --scratch <项目内的编译暂存目录> \
    --temporary-alias <指向该目录的短软链> \
    --output <项目内尚不存在的新目录>
```

> `--scratch` / `--temporary-alias` / `--output` **必须都在项目内**，
> 脚本逐个 `relative_to(project)` 校验，写 `/tmp/...` 会被拒。
> 理由：`build-record.json` 记的是相对项目根的路径 + SHA-256，出了项目就无从复现。
> `temporary-alias` 还得是自己先建好的软链，指向 scratch 那个目录
> （源码路径太长，Swift 编译产物会被路径长度绊住，所以绕一道短软链）。

### 两条铁律

**① 改了源码必须重编；只改包装绝不重编。**

只调整图标、DMG 布局、说明文本这类"包装"时，用：

```bash
bash scripts/build.sh package --app-from-zip <已发布的 zip> --output <项目内新目录>
```

（`--app-from-zip` 走的是「不重编」路径，因此不需要 `--scratch` / `--temporary-alias`，
也不能带 `--icon`——复用的 app 保留它自己那个图标。）

为什么这么严格：Swift 产物不字节可复现。同一个版本号下出现两个不同的二进制，
比不升级更糟 —— 用户无法判断自己手上的是哪一份。

**② 必须是 `--release`。**

### DMG 布局

Finder 在自动化会话里不会把布局写回 DMG（只会落一个 6148 字节的空壳）。
布局改用预置资源 `Resources/dmg-ds-store`，生成与读回走 `tools/dmg_layout.py`。

> 读只读卷必须用 `open(path, 'r')`，默认 `r+` 会报 `Errno 30`。

### 签名

默认 ad-hoc 签名。要做 Developer ID 签名与公证，需要 Apple 开发者账号，
本脚本不覆盖该流程。

**顺序是有讲究的：先 `Contents/Helpers/flashfind-mcp`，再 MyNAS 内二进制，最后主 App。**
主 App 的签名把 `Contents/` 下每个文件的内容纳入封存，反过来做等于只记住了
「签它那一刻 Helper 的样子」，之后再动 Helper 就对不上。本机 `codesign --verify --strict`
未必当场报错，拦你的是别人机器上的 Gatekeeper。

> `codesign --deep` **只许出现在 `--verify` 里**，不要当签名策略。它会按主 app 的身份
> 重签嵌套项、忽略嵌套项该有的 entitlement——ad-hoc 下看不出问题，换成 Developer ID +
> hardened runtime 后就是「内层缺 entitlement」这类难查故障。脚本显式逐个列文件签，
> 新增嵌套二进制没写进列表就签不到，这是刻意的。

签名身份是参数化的（`--identity`，默认 `-` 即 ad-hoc），不写死在脚本里；
非 ad-hoc 时才加 `--options runtime --timestamp`。

### 构建机路径不许进包

`verify_clean.py` 按扩展名扫**文本**，二进制一律被跳过 —— 别把「脱敏检查通过」当成
二进制干净的证据。路径藏在三处，三处分别治：

| 藏身处 | 表现 | 修法 |
| --- | --- | --- |
| Swift 的 STABS 调试映射表（`N_SO` / `N_OSO`） | 主二进制与 helper 里逐文件写着 `/Users/<用户名>/…/client/.ff2-scratch/out/…` | 复制进包后、**签名之前** `strip -S`（签完再动 ⇒ 封存不符） |
| Dart AOT 的源码 URI | `dart compile exe` 传**绝对路径**就把 `…/MyNASCore/lib/*.dart` 嵌进去 | 临时目录里放一份同名副本，cwd 进去、用相对路径编译 ⇒ URI 落成 `MyNASCore/lib/…`；副本与原件按 sha256 逐个核对 |
| 编译日志 | `*.log` 里全是构建机路径 | 日志只写进 `.build/mynas-logs/` 与交付证据目录，`*.log` 进包即失败 |

`build_trial.py` 在组装完、签名前按**字节**扫整棵 `.app`，命中 `/Users/` 就退出，
不生成安装包。这条闸是 1.1.50 补的：此前 1.1.30–1.1.49 的包一直带着这些路径，
因为没人去看二进制里有什么。

### 预览壳与截图钩子

界面截图（README 首图、钉住演示等）不是拿真机截的——真机截图带真实文件名和域名，
脱敏负担重；预览壳里什么都是编好的，零真机信息：

- 预览壳 = 正式包解包，`Info.plist` 加 `FlashFindUIOnlyPreview=true`、换上 DEBUG 二进制后
  ad-hoc 重签。所有钩子都被 `#if DEBUG` + `AppEnvironment.isPreview` 双门挡住，
  **发布构建里整段编译掉**，生产二进制不含这些代码。
- 钩子以环境变量传入（`FF_UI_*`：外观、查询词、窗口宽、钉住、设置页直达等二十来个），
  截图脚本见仓库历史各验收目录的 `证据/shot-*.sh`。
- 演示数据走 `FF_UI_DEMO=1`：三台假来源（群晖 / 飞牛 / OpenList，host 落在
  RFC 5737 的 TEST-NET-1 `192.0.2.0/24`）加两组假文件。文件名是编的，
  **分数仍由 `SearchRanking` 真算、排序仍走 `SearchResultMerge`**——截图里的顺序就是真机行为。
  `FF_UI_DEMO_SECOND=词` 在钉住第一组之后换词搜第二组，演「钉住一批、接着搜一批」。
- ★ 时序注意：程序里改 `query` 会被 SwiftUI 绑定再触发一次 `changedQuery()`，
  同一拍注入的结果会被覆盖回通用夹具——设词与注入结果必须分两个 runloop 拍。

### 交付前

**必须真挂载复核一次**。`hdiutil verify` 查不出"里面少了什么"。

```bash
hdiutil attach 闪寻-1.1.30-arm64.dmg
diskutil info -plist /Volumes/<卷名>   # 卷名以此为准，不要用挂载点名字
ls -la /Volumes/<卷名>
```

顺带看两个常被漏掉的东西：`Contents/Helpers/` 里**只能有** `flashfind-mcp` 一个文件
（多一个少一个都说明打包脚本被改坏了），以及卷内 app 的 `CFBundleVersion` 是不是本次构建号。

## 4. 版本号唯一装配点

`Info.plist` 是版本号的**唯一**来源。界面显示一律走 Core 的 `AppVersion`，
**任何一处都不许自己读 `CFBundleShortVersionString`**（有测试锁）。

`Resources/Packaging/HelperInfo.plist` 是它的**派生副本**，不是第二个事实源。
为什么要有副本：`flashfind-mcp` 是独立命令行可执行文件，`Bundle.main` 不指向宿主 `.app`，
版本得在链接期嵌进它自己的 Mach-O（`__TEXT,__info_plist`）。两份一旦分叉，
编译、链接、单元测试全都不会报错，只有客户端握手那行 `serverInfo.version` 是旧的
——所以打包脚本在链接**之前**比对两份的 `CFBundleVersion`，不一致直接拒。
改版本号记得两处同动。
